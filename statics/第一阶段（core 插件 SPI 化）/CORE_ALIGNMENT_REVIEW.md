# core 现状与目标思想一致性审视（优化项清单）

> 目标思想：以内核为中心、插件化优先、标准化优先、测试前置。  
> 本文用于评估现有 `flexpoint-core` 代码与目标思想的一致性，并给出可执行优化项。

---

## 1. 总体结论

现有 core 已具备可运行骨架（注册、选择、事件、监控、配置、Builder），但距离“可治理的插件化内核”仍有明显差距：

1. **可扩展 ≠ 插件化治理**：已能替换组件，但缺统一插件生命周期与依赖治理。
2. **事件链路存在接线缺口**：存在 EventBus/EventPublisher 抽象，但构建流程未完成统一接线。
3. **并发与一致性边界仍需收敛**：部分实现在线程安全、状态一致性、异常传播上有改进空间。
4. **目标与实现存在语义偏差**：文档强调监控与治理闭环，但 core 中若干关键可观测链路尚不完整。

---

## 2. 与目标思想对齐度评估

| 目标思想 | 当前状态 | 结论 |
|---|---|---|
| 内核优先 | core 功能骨架完整 | ✅ 方向正确，需收敛边界 |
| 插件化优先 | 组件可替换，但无统一 Plugin SPI | ⚠️ 需优先补齐 |
| 标准化优先 | 事件/监控有模型，但契约未统一 | ⚠️ 需统一语义与接口 |
| 测试前置 | 有测试模块，但未形成插件化门槛 | ⚠️ 需建立阶段准入标准 |

---

## 3. 关键优化项（按优先级）

## P0（必须先做）

### P0-1：Builder 未完成事件总线统一接线
**现象**
- `EventPublisher` 使用静态 `eventBus` 发布事件；
- `FlexPointBuilder` 构建流程未显式完成 `EventBus` 创建并注入 `EventPublisher`。

**影响**
- 事件发布路径可能“逻辑存在但实际不生效”，导致监控/治理链路失真。

**建议**
- 在 Builder 统一完成 `EventBus` 创建、注入、关闭生命周期管理。
- 将事件总线纳入 Phase A 插件上下文，避免全局静态散落接线。

---

### P0-2：注册中心并发一致性需收敛
**现象**
- `DefaultExtAbilityRegistry` 用 `ConcurrentHashMap<Class, List>`，但 value 为 `ArrayList`；
- `register/unregister` 使用 `synchronized`，`getAllExtAbility` 非同步读取。

**影响**
- 高并发下可能存在可见性与迭代一致性风险（尤其在读写并发场景）。

**建议**
- 采用 `CopyOnWriteArrayList` 或不可变快照返回；
- 明确并发语义（线性一致/最终一致）并补并发测试。

---

### P0-3：扩展点统计口径疑似存在实现偏差
**现象**
- `FlexPoint#getExtCount()` 通过 `getAllExtAbility(ExtAbility.class)` 计数；
- 注册中心按“具体扩展接口类型”存储，`ExtAbility.class` 可能并非已注册 key。

**影响**
- 总数统计可能不准确，误导治理与诊断。

**建议**
- 统一由 Registry 提供 `getRegisteredCount()` 口径；
- 增加统计口径单测，禁止跨层自行拼计数。

---

## P1（应尽快做）

### P1-1：调用异常传播语义需明确
**现象**
- `EventPublisherInvocationHandler` 通过反射调用方法，异常语义与业务异常透传边界未标准化。

**影响**
- 监控事件中的异常类型、业务侧捕获体验可能不一致。

**建议**
- 规范异常包装/透传策略（是否解包 InvocationTargetException）。
- 对“调用失败/调用异常”事件定义做统一语义约束。

---

### P1-2：事件总线健壮性边界优化
**现象**
- `DefaultEventBus.publish` 在关闭分支先访问 `eventContext.getEventType()`，空值路径鲁棒性可加强；
- 默认线程池配置未纳入统一配置模型。

**影响**
- 边界输入可能触发额外异常；
- 行为不易治理与调优。

**建议**
- 先做 null/非法输入防御式校验；
- 线程池参数收敛到配置中心（并支持插件注入）。

---

### P1-3：选择器体系缺“可解释性”
**现象**
- 当前有选择结果，但缺少“为何命中/为何未命中”的标准输出。

**影响**
- 线上排障成本高。

**建议**
- 在 Phase B 引入 `SelectionDecision` 结构，输出筛选路径、失败原因、候选快照摘要。

---

## P2（后续优化）

### P2-1：静态全局入口逐步收敛
**现象**
- 部分能力依赖静态入口（如 `EventPublisher`）。

**建议**
- 中长期收敛为由 `PluginContext` 管理的实例化依赖，降低全局状态复杂度。

### P2-2：监控处理链标准化
**现象**
- 处理器链可扩展，但指标模型和导出契约未完全统一。

**建议**
- 在 Phase C 输出统一指标字典与导出协议。

---

## 4. 建议纳入 Phase A 的执行修订

1. 将“事件总线统一接线”纳入 Phase A P0 必做项。
2. 将“注册中心并发一致性优化”纳入 Phase A P0 必做项。
3. 将“统计口径统一（ExtCount）”纳入 Phase A P0 必做项。
4. 为以上三项补充单测与并发测试，作为 Phase A 出口门槛。

---

## 5. 建议新增验收指标

- **事件有效性指标**：核心事件发布成功率 >= 99.99%。
- **并发一致性指标**：并发注册/查询 0 数据竞争告警。
- **计数准确性指标**：扩展点统计与注册实数一致。
- **可诊断性指标**：插件加载/失败原因可追溯。

---

## 6. 总结

当前 core 与“内核优先”目标总体一致，但要实现“插件化治理内核”，必须优先修复接线一致性、并发语义、统计口径与异常语义这四类基础问题。建议这些优化项在第一阶段作为硬约束执行，而非后置优化。
