# Flex Point 项目规划（基于 core 现状重制）

> 更新时间：2026-03-24
> 目标：先梳理 `flexpoint-core` 已有能力，再据此制定可落地的项目规划，避免“平台先行、内核滞后”。

---

## 1. core 模块现状能力盘点（As-Is）

> 结论：core 已经具备“可用内核骨架”，包括注册、选择、事件、监控、配置与构建能力；下一步不应从零设计，而应做“能力收敛 + 插件化重构 + 稳定性增强”。

### 1.1 扩展点模型与注册
- 已有统一扩展接口 `ExtAbility`（`getCode()` + `getTags()` + `getExtId()`）。
- 已有标签模型 `ExtTags`，支持字符串/数值/布尔/集合等通用元数据读写。
- 已有默认注册中心 `DefaultExtAbilityRegistry`，支持按扩展类型注册、注销、查询全部实现。
- 注册/注销/查询过程可发布事件，具备生命周期基础观测点。

### 1.2 选择与路由
- 已有 `Selector` / `AbstractSelector` / `SelectorRegistry` 抽象。
- 已有 `DefaultSelectorRegistry`，支持运行时注册、获取、注销选择器。
- 已有 `CodeSelector` 与 `CodeVersionSelector` 默认实现。
- `FlexPoint.findAbility` 已打通：读取 `@FpSelector` → 获取选择器 → 选择目标扩展。
- 已有按 `code`、`code + tags` 的直接查找能力（非注解路由路径）。

### 1.3 调用代理与事件体系
- 通过 `EventPublisherInvocationHandler` 对扩展点调用进行代理埋点（调用前/成功/异常）。
- 已有 `EventPublisher` 统一发布入口与标准事件类型。
- 已有 `DefaultEventBus`（订阅、退订、同步/异步发布、路由器、优先级、关闭）。
- 具备 `EventFilter` / `EventRouter` 扩展点，可做事件过滤与路由。

### 1.4 监控体系
- 已有 `ExtMonitor` 抽象与默认实现（同步/异步）。
- `MonitorFactory` 可按配置创建监控器。
- 已有指标与处理链相关抽象（metrics/collector/alert handler）。
- 说明：监控能力“有骨架”，但标准化输出、插件边界、外部对接契约仍需收敛。

### 1.5 配置与组装
- 已有 `FlexPointConfig`（框架、注册、监控开关及异步参数）。
- 已有 `FlexPointBuilder`，支持自定义 registry / monitor / selectorRegistry 装配。
- `FlexPoint` 已统一编排 ext/selector/monitor/config。

---

## 2. 当前主要问题（Gap）

### G1：已有能力分散，缺少“正式插件 SPI”
虽然 registry / selector / monitor / event 都可替换，但还没有统一的插件生命周期与插件依赖管理。

### G2：事件与监控“能用但不统一”
事件模型、监控指标、处理器链之间缺少统一规范（命名、维度、稳定 API、版本策略）。

### G3：选择器生态未体系化
当前内置选择器较少，组合路由、回退链路、可解释决策还未标准化。

### G4：测试策略未与内核演进绑定
需要把“插件兼容性、并发、回归、性能退化”纳入发布门槛，而不是仅靠功能验证。

### G5：平台化事项时机偏早
治理平台、脚手架、多语言、多平台在内核契约未稳定前推进，会导致重复建设。

---

## 3. 新规划总原则（To-Be）

1. **内核优先**：先稳定 `flexpoint-core` 抽象与行为，再扩展上层能力。
2. **插件化优先**：新增能力默认以插件接入，不改核心主干流程。
3. **标准化优先**：先统一事件/指标/错误/版本语义，再做平台与生态。
4. **测试前置**：每个内核迭代都附带测试矩阵与兼容声明。
5. **平台后置**：平台与生态建设以后置里程碑推进。

---

## 4. 分阶段项目规划（重制版）

## Phase 0（最高优先级）：现有内核优化（前置整治）

> 配套文档目录：`statics/第0阶段（现有内核优化）/`
> - 技术方案：`TECHNICAL_DESIGN.md`
> - 子任务拆解：`TASK_BREAKDOWN.md`

### 目标
先解决 review 暴露的内核基础问题（事件接线、并发一致性、计数口径、异常与边界鲁棒性），为插件 SPI 化提供稳定底座。

### 关键任务
- [ ] Builder 统一完成 EventBus 创建、注入与关闭管理
- [ ] Registry 并发一致性优化与并发测试
- [ ] 扩展点计数口径统一（总数/分类型）
- [ ] 调用异常语义与事件语义边界收敛
- [ ] 事件总线边界健壮性与配置化治理

### 验收标准
- 事件链路端到端可验证，核心事件可稳定消费
- 并发读写场景无数据竞争告警
- 统计口径与实际注册数据一致

---

## Phase A（核心阶段）：core 插件 SPI 化（1~2 个迭代）

> 配套文档目录：`statics/第一阶段（core 插件 SPI 化）/`
> - 技术方案：`TECHNICAL_DESIGN.md`
> - 子任务拆解：`TASK_BREAKDOWN.md`
> - core 对齐评审：`CORE_ALIGNMENT_REVIEW.md`

### 目标
在现有 core 骨架基础上建立统一插件协议，使 selector / event / monitor / metadata 都能以一致方式加载与治理。

### 关键任务
- [ ] 定义统一插件接口：`Plugin`、`PluginDescriptor`、`PluginLifecycle`。
- [ ] 增加插件管理器：安装、启停、排序、依赖检查、冲突检测。
- [ ] 定义插件隔离边界（命名空间、能力声明、版本约束）。
- [ ] 将现有 `CodeSelector`、事件订阅、监控处理链改造为“官方内置插件”。
- [ ] 在 `FlexPointBuilder` 中增加插件装配入口。

### 验收标准
- 新增一个选择策略无需改 `FlexPoint` 主流程。
- 插件可独立启停，停用后系统可降级运行。
- 插件冲突可在启动期被识别并给出明确错误。

---

## Phase B：选择与路由体系增强（紧随 Phase A）

### 目标
把“能选中”升级为“可组合、可解释、可回退”的标准选择体系。

### 关键任务
- [ ] 内置插件补齐：`tenant`、`gray`、`ab-test`、`code-version`。
- [ ] 增加组合选择器（链式/加权/回退）。
- [ ] 增加选择决策解释模型（输出命中路径与过滤原因）。
- [ ] 统一选择失败语义（无匹配、多匹配、配置缺失）。

### 验收标准
- 主流场景（租户+版本+灰度）可通过组合策略配置完成。
- 线上问题可通过解释信息快速定位“为何命中/未命中”。

---

## Phase C：事件与观测标准化（仍属于 core）

### 目标
基于已有 EventBus/Monitor 能力，统一事件与指标标准，形成平台化基础数据层。

### 关键任务
- [ ] 统一事件字典（类型、字段、扩展属性约定）。
- [ ] 统一指标模型（QPS、延迟分位、错误率、选择命中率）。
- [ ] 建立观测插件接口（metrics/log/trace）。
- [ ] 输出最小可用导出层（如日志/REST），不做重平台 UI。
- [ ] 明确异步处理与背压策略。

### 验收标准
- 事件与指标定义可供外部平台直接消费。
- 监控与事件在高并发下行为可预测且可压测验证。

---

## Phase D（后置）：平台化、脚手架、多语言、多平台

### 范围
- 监控与治理平台
- 脚手架/IDE 插件
- 多语言 SDK
- 多平台与生态运营

### 启动前置条件（必须全部满足）
- [ ] core 插件 SPI 连续 2 个小版本保持兼容。
- [ ] 选择体系、事件体系、观测体系已标准化。
- [ ] 内核测试矩阵稳定运行（单测/并发/兼容/性能基线）。

---

## 5. 测试与发布规范（强制执行）

### 5.1 测试矩阵
- 功能测试：注册/注销/查找/选择/组合路由。
- 兼容测试：旧插件在新内核版本可运行。
- 并发测试：事件发布、插件启停、选择调用并发场景。
- 性能测试：调用耗时、异步队列、事件处理吞吐。
- 回归测试：每次 core 变更必须跑全量核心回归。

### 5.2 发布门槛
- core 变更必须包含：设计说明 + 测试 + 兼容性声明。
- 破坏性变更必须有迁移指南。
- 无测试/无兼容说明的 core 变更不得发布。

---

## 6. 模块职责重申（按新规划）

- `flexpoint-core`：唯一主战场（插件 SPI、选择路由、事件观测、稳定 API）。
- `flexpoint-common`：跨模块契约与异常语义。
- `flexpoint-spring`：装配与集成适配，不承载核心决策逻辑。
- `flexpoint-springboot`：自动配置、插件自动发现与装配。
- `flexpoint-test`：核心测试矩阵与兼容/性能基线。
- `flexpoint-examples`：插件化实践示例，不做平台功能堆砌。

---

## 7. 里程碑结论

本次重制后的路线不是“推倒重来”，而是基于 `flexpoint-core` 已有能力进行结构化升级：
- 先把现有骨架收敛为统一插件内核；
- 再补齐选择、事件、观测标准化；
- 最后再推进平台、脚手架、多语言与生态。

即：**一切平台能力都必须建立在稳定内核体系之上。**
